# PRD v1.5 深度评估报告

> **评估人**：MiMo (AI Tech Lead)
> **日期**：2026-07-22
> **评估范围**：PRD-UniRoute-v1.5.md 全文 + 10 轮顾问讨论 + 6 竞品分析 + 7 篇前沿研究
> **评估标准**：作为开发团队唯一 source of truth 的可执行性

---

## 一、总体评价

**评分：72/100**

PRD v1.5 是一份经过 10 轮迭代打磨的文档，信息密度极高（1379 行），覆盖了从产品定位到数据库 Schema 的完整链条。作为"产品思考"文档质量很高，但作为"开发依据"文档存在系统性缺陷。

**核心问题**：这是一份**产品设计文档**，不是**工程规格文档**。它告诉开发者"做什么"和"为什么做"，但在"怎么做"和"做到什么程度"上存在大量模糊地带。

## 二、优点（值得保留的部分）

### 2.1 计费状态机设计（90/100）
- Freeze/Settle/Cancel 三态模型清晰
- 预冻结公式经过 v1.1→v1.2 两次修正，最终版本合理
- 幂等性设计（freeze_idempotency 表）考虑周全
- 安全余量系数（safety_factor=1.5）和最低冻结金额（MIN_FREEZE_AMOUNT=10）有实际意义

### 2.2 用户旅程设计（85/100）
- 管理员 Onboarding（< 30 分钟）和开发者接入（< 5 分钟）有明确的时间目标
- 从部署到首次调用的完整路径清晰
- 可作为验收测试的基准

### 2.3 错误码体系（80/100）
- `{category}.{specific}` 两段式结构清晰
- OpenAI 兼容的错误响应格式
- upstream_error 嵌套结构考虑了上游错误透传

### 2.4 技术路线决策（85/100）
- 基于 OneAPI Deep Fork 的决策经过竞品分析验证
- "完全放弃与上游同步"避免了维护噩梦
- 模块化单体架构适合 3.5 人团队

### 2.5 合规与安全方案（80/100）
- 本地部署优先策略正确
- API Key HMAC-SHA256 + 渠道 Key AES-GCM 的分层加密合理
- 软删除 + 审计日志的合规基础

## 三、缺陷（需要修正的部分）

### 3.1 🔴 致命缺陷

#### 3.1.1 无 OpenAPI Spec（0/100）
PRD v1.5 附录 E 写道："待开发完成后补充 OpenAPI/Swagger 文档"。

**问题**：这是一个 API 网关产品，API 是核心交付物。没有 OpenAPI Spec 意味着：
- 前后端无法并行开发
- 接口定义分散在 PRD 的各个角落，容易遗漏
- 无法自动生成客户端 SDK
- 无法做契约测试

**影响**：开发过程中必然出现接口不一致、字段遗漏、前后端联调困难。

#### 3.1.2 前端技术方案自相矛盾（20/100）
PRD v1.5 明确写道："保留 OneAPI 原生前端（React 18 + Semi Design + Vite）+ 新增页面用 Tailwind（禁用 preflight），路由级分离"。

但 `docs/tech-ref/06-frontend-spec.md` 写道："统一 Semi Design 可以复用 OneAPI 原生组件"，"3.5 人团队维护两套 CSS 框架（Semi + Tailwind）成本过高"。

**实际实现**：前端既不用 Semi Design 也不用 Tailwind，用的是纯 CSS + inline styles。

**问题**：三份文档三个方案，开发者无所适从。

#### 3.1.3 计费公式关键参数未定义（30/100）
预冻结公式引用 `default_max_output_tokens`，但 PRD 未定义：
- 具体数值是多少？（4096? 8192? 模型相关?）
- 按模型查表还是统一默认值？
- 如果客户端传了 max_tokens 但值异常大（如 100000），是否限制？

**影响**：计费模块的核心公式无法直接实现。

### 3.2 🟠 重大缺陷

#### 3.2.1 流式请求的 Token 计数机制不明确（40/100）
PRD 写道："每 100 Token 检查余额"和"客户端断开 → context.Canceled → 关闭上游 → 按已收到 chunk 结算"。

但未定义：
- 如何在流式 chunk 到达时实时计数 Token？（chunk 是 SSE 格式，需要解析 `data:` 行）
- 计数的是 `usage` 字段还是自行估算？
- 如果上游不返回 usage（很多厂商不返回），如何估算？
- "每 100 Token 检查余额"的实现方式：是累计到 100 才检查，还是每 chunk 都检查？

**影响**：流式计费是系统的核心难点，PRD 把最难的部分留给了开发者自行决策。

#### 3.2.2 上游 429/5xx 处理策略缺失（30/100）
PRD 定义了熔断器状态机（HEALTHY→OPEN→HALF_OPEN），但未定义：
- 上游返回 429 时，是重试下一个 Key 还是直接返回 429 给客户端？
- 上游返回 5xx 时，重试几次？间隔多久？
- 熔断期间的请求如何处理：排队、快速失败、还是降级？
- 不同错误码（429 vs 500 vs 502 vs 503）的处理策略是否不同？

**影响**：网关的可靠性核心逻辑无法确定。

#### 3.2.3 敏感词拦截规格不完整（35/100）
PRD 提到"DFA 敏感词前置拦截（零成本）"，但未定义：
- 初始词库来源（内置哪些词？）
- 管理界面如何添加/删除词？
- 匹配后的处理：拒绝请求？记录日志？两者都有？
- 检查范围：只检查 user message？还是也检查 system prompt？
- 是否支持正则表达式？

**影响**：F13 功能无法验收。

#### 3.2.4 分页规格不统一（40/100）
PRD 提到"分页"但未统一定义：
- 默认 page_size 是多少？（10? 20? 50?）
- 最大 page_size 是多少？
- 使用 offset 分页还是 cursor 分页？
- 响应格式：是否包含 total_count? has_more?

**影响**：每个列表接口的实现可能不一致。

#### 3.2.5 渠道测试端点规格缺失（30/100）
`POST /api/v1/channels/{id}/test` 被提及，但未定义：
- 用什么模型测试？（从 channel 的 models 中随机选？还是固定用便宜模型？）
- 发送什么内容？（固定 prompt? 空 prompt?）
- 成功/失败的响应格式？
- 超时时间？
- 是否扣费？

**影响**：渠道测试功能无法验收。

### 3.3 🟡 中等缺陷

#### 3.3.1 单 Org 假设未明确（50/100）
PRD 提到多 org 架构，但实际实现和很多设计细节都假设单 org（如 wallet 查询直接取第一个 org）。PRD 应该明确：
- Phase 1 是否支持多 org？
- 如果单 org，admin 用户和 org 的关系是什么？

#### 3.3.2 CSV 导出格式未定义（40/100）
`GET /api/v1/wallet/transactions/export` 被提及，但未定义：
- CSV 列名和顺序
- 日期格式
- 金额单位（分还是元？）
- 编码（UTF-8 BOM?）

#### 3.3.3 系统设置的 Key-Value 规格不完整（45/100）
Settings 表是 key-value 结构，但 PRD 未定义：
- 有哪些预置 key？
- 每个 key 的值类型和验证规则？
- 哪些设置修改后需要重启服务？

#### 3.3.4 日志保留策略过于简单（50/100）
PRD 提到"软删除 + 每日备份"和"log retention"，但未定义：
- 保留多少天？
- 超期数据是物理删除还是归档？
- 备份策略（pg_dump 频率、存储位置）？

#### 3.3.5 预算告警的触发条件和通知方式不完整（45/100）
PRD 提到"余额 < 阈值触发 webhook 告警"，但未定义：
- 阈值如何配置？（环境变量? 数据库设置?）
- 告警频率限制（每小时最多一次?）
- webhook payload 格式？
- 是否支持邮件通知？

### 3.4 🔵 轻微缺陷

#### 3.4.1 模型列表合并逻辑不清晰（55/100）
`GET /v1/models` 需要合并多个渠道的模型列表，但 PRD 未定义：
- 去重规则（同名模型不同渠道，返回几个？）
- 排序规则
- 只返回 status=active 渠道的模型？

#### 3.4.2 审计日志的 action 枚举不完整（50/100）
PRD 列出了一些 action（key.create, channel.update 等），但未完整枚举所有可能的 action 值。

#### 3.4.3 组织倍率（org_model_prices）的生效逻辑不清晰（50/100）
当 org_model_prices 有记录时，是完全替代 model_prices 还是相乘？PRD 说"乘以 multiplier"但不够明确。

## 四、遗漏（PRD 未覆盖但开发需要的内容）

### 4.1 数据库索引策略
PRD 定义了表结构但未定义索引。对于查询频繁的表（call_logs, transactions），索引设计直接影响性能。

### 4.2 连接池配置
PostgreSQL 和 Redis 的连接池参数（max_conns, min_conns, max_idle_time）未定义。

### 4.3 请求超时配置
- 上游请求超时时间？
- 客户端请求超时时间？
- 可配置还是硬编码？

### 4.4 日志格式
- 结构化日志还是纯文本？
- 日志级别（DEBUG/INFO/WARN/ERROR）？
- 敏感信息脱敏规则？

### 4.5 API Key 的 allowed_models 通配符
PRD 提到 "allowed_models: gpt-5,deepseek-v4-pro"，但未定义：
- 是否支持通配符（如 `gpt-*`）？
- `*` 或空值是否表示"允许所有模型"？

### 4.6 限流的 Redis Key 设计
RPM/QPS 限流使用 Redis 滑动窗口，但 PRD 未定义：
- Key 的命名规则（如 `ratelimit:{key_id}:{window}`）
- 窗口大小（1 分钟? 1 秒?）
- 限流响应格式（429 + Retry-After header?）

### 4.7 静态资源服务
PRD 提到"Go 二进制内嵌静态资源"，但未定义：
- 内嵌方式（embed.FS? 还是 Nginx 提供?）
- 前端路由的 SPA fallback 策略

---

## 五、总结

PRD v1.5 作为产品设计文档质量很高（85/100），但作为开发依据文档（72/100）存在系统性缺陷：

| 维度 | 评分 | 说明 |
|------|------|------|
| 产品愿景 | 90/100 | 定位清晰，差异化明确 |
| 用户旅程 | 85/100 | Onboarding 和开发者接入路径清晰 |
| 计费设计 | 85/100 | 状态机合理，但公式参数不完整 |
| API 规格 | 30/100 | 无 OpenAPI Spec，端点定义分散 |
| 前端规格 | 25/100 | 技术方案矛盾，页面规格不完整 |
| 错误处理 | 75/100 | 错误码体系好，但上游处理策略缺失 |
| 安全规格 | 80/100 | 加密方案好，但敏感词规格不完整 |
| 运维规格 | 50/100 | 部署方案好，但监控/备份/日志不完整 |
| 可测试性 | 40/100 | 验收标准存在但不具体，无法直接写测试 |

**结论**：PRD v1.5 需要补充一份"技术规格附录"，将分散在各章节的 API 定义、前端规格、错误处理策略等统一整理为可执行的工程规格。这份附录不是推翻 PRD v1.5，而是让它变得可执行。
