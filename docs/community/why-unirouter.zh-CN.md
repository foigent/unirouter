# Why UniRouter / 设计理念

[English](why-unirouter.md) · [项目介绍](../../README.zh-CN.md)

企业需要掌握 AI 如何执行、费用如何产生，以及判断所依据的事实。UniRouter 从模型执行开始，把接入、路由、用量、账务和可检查的记录连在一起；X-Insight 进一步把分散在不同来源中的事实组织成可调查、可理解的证据。

## 从自己的经历出发

我在 ToB 行业做了二十多年销售，经历过 HP、Dell、Oracle、SAP 等外企在中国的发展，也参与过开源和创业公司的业务。当 AI 开始变得可用，我首先感受到的是危机：如果不亲自理解这项技术，过去积累的经验，还能支撑我走多远？

离开上一家创业公司、考完研究生考试后，我在 2026 年初开始研究机器人和 AI。逐步探索之后，我选择从更贴近自己基础设施、数据库和企业应用经历的 AI 基础设施入手。Paul Graham 所说的 [Stay upwind](https://www.paulgraham.com/hs.html) 给了我启发：选择能够为未来打开更多可能性的事情，从一个具体问题开始，在实践中学习。

与一些 CIO 的交流，让问题变得具体。我看到两种状态：一些企业由管理层推动，迅速采用 AI，安全与数据治理还来不及跟上；另一些企业则因为无法确定敏感信息会被怎样使用，而迟迟难以迈出下一步。

其中一个具体担忧是：员工可能只是想把工作做好，就把企业内部的敏感业务资料交给了外部模型。有意披露也是风险，但正常使用本身就带来了问题：哪些信息可以离开企业，由谁授权，事后还能查到什么依据？

AI 让知识更容易被提取、重组和复用。我想探索的是，企业怎样在受益于这些能力的同时，掌握自身信息的使用边界，并让实践中的积累继续产生价值。

## 为什么从模型网关开始

网关为经过它的模型请求提供了一个执行策略的位置。应用和 Agent 可以使用共同的接入点，企业则能够管理权限、可用模型、预算与执行记录。

已有网关已经解决了其中不少问题。LiteLLM 提供路由、预算控制、费用追踪和安全护栏集成；New API 提供渠道管理、额度核算，以及预扣、结算和退款机制。自主部署、接口兼容和记录用量，都是共同能力，不能仅凭这些说明 UniRouter 的差异。

UniRouter 重点关注让执行依据可以被检查：这次调用由哪套经过验证的配置放行，经历了哪些上游尝试，用量来自哪里，又如何形成费用。[基于源码的设计比较](gateway-design-comparison.md)记录了支撑这一定位的具体机制，以及比较的适用范围。

例如，应用没有收到回答，于是发起重试。要理解这次调用，就需要区分上游尝试、客户端交付、实际报告的用量和最终账务状态。仅凭一次 HTTP 成功响应，无法回答所有这些问题。

## 由此形成的设计取舍

**让执行绑定经过检查的配置。** 在规范执行路径中，UniRouter 会在发起调用前检查选定的发布版本、封存的路由清单和适用的供应商资格，并在提交路由决定与上游尝试记录后授权调用。这为后续调查保留了具体的执行依据，也增加了模型资格验证的工作量，以及请求对数据库的依赖。

**让账务事实能够恢复和核查。** 预留记录保存执行绑定、计费模式和定价依据；结算与待发送的账务事件在同一事务中提交，未完成的结算有对应的恢复路径。供应商报告的用量、估算值、计算金额和客户扣费保留各自的含义，为解释费用和调查失败提供依据。具体运行效果仍需在受支持的环境中验证。

**有选择地采集数据。** 自主部署让企业能够管理自己的网关和本地记录；发送给远端模型的请求仍然会离开这一环境。当前实现包含可选的、限定范围的内容采集，并对保留时间、容量和访问授权分别约束。控制采集与识别、阻断敏感内容外发，是不同的能力。这些机制不能证明已经具备完整的数据防泄漏能力，也无法覆盖绕过网关的请求。

**由负责动作的系统保留决定权。** UniRouter 管理自身范围内的模型调用，工具动作和业务结果则由对应系统负责。模型给出了回答，并不能证明发票已经开出，或者客户已经接受报价。

**通过明确的接口连接其他系统。** 兼容广泛使用的模型接口，降低接入成本；通过经过验证的执行配置，明确不同供应商的能力差异。观测与调查应当能够独立演进，扩展能力也需要清楚的权限和数据约定。

## X-Insight 在其中的位置

UniRouter 可以独立使用，负责模型执行、自身账务和来源记录。X-Insight 是独立的证据与调查产品，用于关联不同来源的事实、调查相关活动。它通过异步接口消费经过授权的事实，不成为模型请求的同步依赖，也不接管 UniRouter 的执行决定。

这样的分工让用户可以先使用网关，再按需要引入调查能力。X-Insight 的许可证、发布版本和受支持的集成分别说明。当前来源合同区分执行上下文、身份和费用依据，保留记录版本，并明确表达未采集等缺口；内容访问有独立的授权边界。[设计比较与实现依据](gateway-design-comparison.md)记录了此次核对的范围，并区分接口能力与交付准备情况。

## 更长期的探索

我判断，未来会有更多工作围绕人与 Agent 共同完成的目标展开。理解这些工作，需要把模型执行与其他系统记录的任务、动作和结果联系起来。

我更长期的兴趣是：这些观察能否帮助企业持续修正对业务对象、关系和流程的理解，形成由真实工作不断补充的业务本体？这仍然需要领域知识和人的验证，仅凭活动记录，无法直接确定意图、因果关系或业务成功。

UniRouter 现有实现已经包含模型接入、策略、路由、用量、账务和请求记录。具体支持范围与验证结果依赖版本、供应商和环境，[源码比较](gateway-design-comparison.md)记录了此次核对的候选版本与尚未完成的交付条件。近期工作着眼于让首次使用路径可复现、接口更易集成；跨来源的调查体验由 X-Insight 独立完善。自动理解业务与优化工作流程，则属于更长期的研究方向。

## 为什么选择开源

开发过程中，我越来越清楚最初的构想与企业真正能用的产品之间有多大距离。随着 Agent 承担更多工作，框架和集成要求也持续变化。仅靠我一个人追赶所有适配，难以持续。

我希望把反复出现的需求沉淀为可重复使用的产品能力，让用户能够更自主地采用产品，让一次改进惠及更多部署。这是我想追求的产品驱动增长。

开放项目，让使用者有机会检查关键机制、检验产品假设，并把真实使用中的改进带回来。我不是开发出身，积累更多来自客户、市场和销售；我希望贡献这些经验，也向具有不同工程与产品视角的人学习。问题反馈、文档、测试和边界清楚的集成，都是有价值的参与方式。

我希望通过这样的协作，把 UniRouter 做成有用的产品，也拓展自己在下一段职业生涯中需要的能力。一起参与项目，可以从[贡献指南](../../CONTRIBUTING.md)开始。
