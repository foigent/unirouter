## 精确主体与优先级

目标选择键是 `(org_id, project_id, authenticated UR personal owner_user_id?)`。`ActualHuman` 在现有源码只能是 `unknown`（`internal/executioncontext/context.go:127-141`）；不能用它匹配用户例外，也不能把 API key 的 owner 冒充实际发起人。仅当网关已认证 key `key_type=personal` 且 `owner_user_id>0`、用户及项目成员仍有效时进入该项目的 UR 账户例外；service/shared key 只走企业→项目，纵使管理所有者字段存在也不成为用户例外。源依据：`internal/middleware/auth.go:270-330`、`execution_context.go:33-68`。无主体或读失败时不得误落“全部保存”；以有界 capture gap/未确认状态处理，执行与财务结果不变。

策略作用域为一份企业默认（org）、已有项目策略行（org+project）和项目内 UR 账户例外（org+project+user）。新/旧项目无显式项目行时读取企业默认；企业默认未建时保留旧部署默认以兼容升级。已有 `execution_content_policies` 行均按显式项目策略解释，迁移不把旧写入悄悄变成继承。user 例外必须有明确主体与来源，不允许通配帐号。**已授权的显式例外按 user → project → enterprise → legacy deployment 选择最具体配置**；企业默认不是新发明的组织强制上限。冲突样例：企业 full / 项目 disabled / 用户 full，对匹配的个人 key 是 full、其他 key 不保存；企业 disabled / 项目 full，该项目仍按 full；企业 full / 项目 full / 用户 disabled，匹配个人 key 不保存。企业“默认关闭”页面必须列出仍启用的显式例外及覆盖范围，不能标成全域绝对关闭。部署级 hard-disable 和物理上限始终不可放宽。若将来需要全域不可例外的禁存操作，另定明确产品合同，本次不编码。

只有实际 `effective` 状态授权 capture；`desired` pending/failed 不得提前生效。部署 `PAYLOAD_CAPTURE_MODE=disabled` 是物理硬停；`SOURCE_CONTENT_FULL_ENABLED`、绑定的文件存储就绪、实际支持的 protocol/observation point、部署 32 MiB 上限均不可被策略提升（`internal/contentcapture/policy_store.go:121-170`、`cmd/uniroute/content_runtime.go:35-75`）。企业默认 full 的产品目标通过管理员明确配置并核对环境能力后实现，不把部署默认从 metadata_only 偷换为无条件 full。

D20 在**当前解析后的作用域**收敛为三个可解释的呈现模式：①保留复查正文（`full_content` 及期限，并允许必要执行暂存）；②仅执行必需暂存（复查正文 disabled/metadata、Cache 不读写新请求正文）；③严格不持久保存正文（复查正文 disabled/metadata，拒绝依赖持久暂存的新异步任务）。底层沿用现有 review `mode`，另加一个精确的执行暂存约束，不造通用策略引擎；`full_content` 与 strict 同时生效是非法组合，写入和解析均应拒绝。企业默认可由获授权的项目/个人明确例外覆盖，UI 列出范围；企业默认 strict 不等于全域 hard stop。部署 hard-disable 仍单独优先。当前 `ScopedPolicyInput` 已把执行暂存约束与 review `PolicyConfig` 从**同一获选层**解析，拒绝最终 `full_content + strict_no_persist`；仍无数据库持久化、权限重验或 Cache／媒体接线，不能被当作完整 D20 运行实现。

## 数据与配额不变量

保留现有 `execution_content_policies` 为每项目唯一配额账本；`reserved_bytes`/`stored_bytes` 是真实项目累计，不随每个 user 例外另开额度。新增企业默认行及 user 例外行只保存 desired/effective config、版本、时间、应用状态，不复制对象计数。**项目额度基线必须独立于 capture mode**：现有 `PolicyConfig.Validate` 禁止 disabled/metadata 配置携带 `quota_bytes`，但企业或项目默认 disabled 时，显式个人 full 例外仍需要一个已定义的项目总额度，不能合成无限/私有额度。候选为企业级“每项目默认额度”及可选项目覆盖值；解析器要求调用者传入已解析的正数 `ProjectQuotaBytes`，未提供则拒绝个人 full。项目显式 8 GiB 可覆盖企业给该项目的 5 GiB 默认额度（仍受部署资源/校验上限），不取祖先最小值。user 例外**无专属 quota 字段**，仅控制 capture 开关、期限、单项上限和已支持的类型，消耗选定项目的同一额度。企业默认 30 天、项目显式 90 天时按 90 天，除非实际部署硬限制更小；不能取所有层最小值令例外失效。`allowed_purposes` 保持现有 `human_review`，不扩大 read grant；`redaction_ref` 当前不支持。正文对象继续冻结实际 effective config/version/时间，manifest 显示精确 policy source、capture completeness/reason；历史对象不因后续 policy 改变被改写。

现有 `PolicyStore.Reserve` 在一笔事务中锁 stream→项目 policy→object，并对**项目 policy effective version**核对后更新项目额度（`internal/contentcapture/reservation.go:95-211`）；仅修改 `Begin` 的策略选择会导致 user/enterprise 版本不匹配或绕过禁存。实现必须让 `Begin` 与 `Reserve` 在同一授权模型下重验有效作用域及版本，维持统一项目额度和锁顺序；不能先读 user 再用旧项目 row reservation。项目无 row 而继承 enterprise full 时，也要在已验证事务中建立项目配额行，且该行与“显式 override”有可查询标识，不可因分配额度就停止继承后续企业更新。曾经 reserve 的对象继续按冻结的历史策略完成发布/过期回收，当前禁存只阻止新 capture。迁移需覆盖旧行、无行新项目、已有对象/额度与回滚前态。

网关当前 `contentcapture.Observation` 只含 org/project/request/protocol/point/attempt/media/time，没有 owner 或 key type（`internal/contentcapture/http.go:11-17`）；client 与 provider capture 共用这个结构（同文件 `23-85`）。故 user 例外还需把**已认证且已验证的** personal owner 选择证据由网关传入，但不得把 caller 自带 user ID 或 `ActualHuman` 作为 authority。source manifest/object 的单个数字 `policy_version` 目前也绑定项目 policy 行；加入多层版本后必须保存 scope-qualified ref 或版本向量，不能把用户版本碰巧相同的数字当同一权威。

## 读取、写入与版本

**编码前锁顺序和兼容门禁（2026-09-29 裁定后预检）。** 管理 PUT 现有 `reauthorizeCommittingActorTx` 先锁 actor user/session，再锁 org/project（project 为 `FOR UPDATE`），个人项目权限再锁 membership；`PolicyStore.PutTx` 随后锁项目策略行。成员变更先锁 actor/target user，再锁 project/membership，可能在 membership 降级后触发 personal credential 禁用。因此新 scoped PUT 不得先拿策略行、再反向索取 project/user/member/key。新 capture／Cache／媒体提交事务应固定为：已认证个人 owner 的 user（如适用）→org→project→member（如适用）→当前 key→stream（仅 capture）→企业默认→项目唯一账本/覆盖行→个人例外行→对象/任务行；同一组主体按 ID 稳定排序。主体及 scope 权限读取用足以阻止并发撤权的可共享行锁（通常 `FOR SHARE`），不把每次请求升级为 `FOR UPDATE`。不存在企业默认行时，企业 PUT 和读取以同一 `orgs` 父行互斥（管理写锁、读取共享锁）后再判定缺席；不存在个人例外行时，以已存在的项目唯一账本行作共同父范围，管理插入拿写锁，Reserve 拿写锁、Cache/媒体拿共享锁，然后读取或插入，不能仅锁命中的例外行。项目账本首次创建则先在精确 project 父行下建立并重读，不把临时创建误标为显式覆盖。现有 Reserve 是 stream→project policy→object；必须把身份/成员锁放在 stream 之前，并保证管理 PUT 不在持有策略行时回头取身份锁。Cache 与媒体不取 content stream 锁。key 撤销/成员变更与上述次序的并发交错需要实际 PG 双会话测试；若当前管理路径与此顺序冲突，先修锁顺序，不以锁超时或重试掩盖。Begin 的只读结果仅供早期判定，Reserve/Cache commit/媒体新建须在自己的事务内重新取有效层、主体、版本和模式。

正式 C v1 `Capture.policy_ref` 是非控制字符且最长 128 的文本，`policy_version` 是最长 19 位的正十进制字符串，且 `Capture` 禁止额外字段（`contracts/source-content/v1/c0-contract.schema.json`）。现有 UR 发布校验硬编码项目 ref `content-policy:org:project`；新 ref 必须在**原字段**中编码 scope 和身份：历史及继续显式的项目 ref 保持 `content-policy:<org>:<project>`，企业继承使用 `content-policy:<org>:enterprise`，个人例外使用 `content-policy:<org>:<project>:user:<owner>`；version 仍是所选作用域的正十进制 effective version。层版本向量和继承行状态留在 UR 内部 Reservation／对象快照，不增 C v1 wire 字段。历史项目 ref 与数字版本维持读取；新对象发布校验应比较冻结的精确 ref、版本及内部向量，而非仅比较可能撞号的数字。XI 现有 C v1 decoder 的兼容性已在其只读工作树用临时 Go overlay 验证：`GOTOOLCHAIN=local GOPROXY=off go test -overlay /private/tmp/ur-xi-policy-wire-compat-20260929/overlay.json ./internal/sourcefacts -run ^TestRootScopedPolicyWireCompatibility$ -count=1` 通过。用例覆盖历史项目 ref、企业 ref、个人 ref 的 manifest/page 解码与冻结引用匹配；同号数字但改变 ref 被拒，额外 `capture` 字段被拒。测试没有修改 XI 源码，也不证明 UR 新对象冻结和发布接线已完成。

下一 schema head 若为 M122，expand migration 必须在 `runtime_generations` 锁下检查所有非 stopped generation 的不可变 support manifest 含 M122 和新内容策略/媒体期限实现身份；旧二进制不得与新策略/期限行共存。`schemaauthority` 的 exact-ledger 启动检查和 manifest 应纳入本次变更。down migration 在存在任何新作用域策略、新 deadline job、非 stopped generation 或其他新身份写入时拒绝降级；不能删除期限列后让旧 runtime 对已接收任务无限派发。旧任务 deadline 为 NULL，不回填、不静默缩短，回滚前保留解释能力。正式部署/rollback gate 需基于该机制验证，不能以一次本地迁移通过代替 Target 证明。

保留 `GET/PUT /api/v1/projects/{id}/payload-policy` 管理路径和版本 CAS 的已有行为；新正式 V2 resolved view 要分别给出每层 `policy_ref`、desired/effective 版本/状态、真正有效 config/source、部署 gate/storage 状态及仍启用的显式例外，避免一个 numeric `policy_version` 同时指代多层。每层写入带该层最新版本及引用；如继承路径变动或范围行插入，返回 409 并要求新读，不能以撞号版本误接受。企业/项目/用户配置分别由被授权的 UR 管理员维护；项目管理权限不得升级为企业默认修改权。列表/发现端点只返该 actor 有权选择的项目/用户身份，不含 key、secret、正文，且校验账户仍属当前组织/项目。

XI 主入口主动保存时，XI 先保存自己的期望与版本，再经正式 UR 策略写入，回读 desired/effective/application 和版本；网络不确定时标为 `unconfirmed`，不推断成功；pending/failed 不能称生效。XI 后续读到 UR 独立改动时显示 drift，让有权管理员选择“按 UR 最新版本恢复 XI 意图”或“接受 UR 当前值”；绝无周期性自动覆盖。原 `GET/PUT` 只认 UR 用户 JWT/项目管理员（`internal/admin/content_policy.go:43-90`），source-read key purpose 仅可读来源内容（`migrations/000116_execution_source_facts.up.sql:21-41`、`000119_execution_content_capture.up.sql:58-70`），不能借用。

服务写入候选须先核查现有配对控制/凭据模型能否复用受限能力；如不能，才增最小的 `xinsight.policy.manage` 目的，精确绑定 source instance、org、项目集合与策略读写作用域，无 Gateway/Provider、正文 read、连接生命周期及其他 admin API 权限。机器身份本身不产生管理权；**UR 管理员明确委托给精确配对 XI 的 scope/action** 才是授权来源，UR 每次提交事务内重验委托仍有效、credential active、org/project、动作与版本，连同 service actor、XI 认证操作员的来源引用及旧新版本写 audit。XI 上报的操作员仅为审计来源，不冒充 UR 用户，也不能凭 JSON 的 `actor_user_id` 获得权限。不预设所有 XI 管理员都映射 UR 个人账户，不先新建签名 PKI。这里未选择凭据生成/复用、分发、费用与生命周期，不创建或写入任何真实凭据；当前 UR data-exchange control 仍包在管理员路由下（`cmd/uniroute/main.go:1252-1273`），尚不能证明已有 XI→UR 的机器写入权。

现有 audit helper 默认从 UR JWT context 取 `user_id` 并写入 `audit_logs.user_id`（`internal/admin/audit_handlers.go:265-303`），所以服务调用不能假造一个普通 UR 用户 ID 来复用 helper。实现需明确区分明确委托的 UR 管理员、机器执行者与 XI 来源操作员，并保持同事务可查询审计；若沿用真人映射，提交时重新核对该 UR 管理员的委托权限，若另建 service actor 表示，则迁移/audit reader 都须识别它。此项是身份与审计合同触发项。

## 负向矩阵与代码前审查点

源码定向 writer 核查（不替代运行验证）：`internal/traceutil/metadata.go:5-177` 对 trace metadata 做字段 allowlist，拒绝嵌套对象，但允许某些任意字符串截断至 256 字节；因此允许字段的赋值来源仍需核对，不能以 allowlist 一项证明无正文。当前生产 `call_logs` writer `internal/gateway/evidence_materializer.go:436-465` 不写 `upstream_error`；该列仍被管理日志 API 读取（`internal/admin/log_handlers.go:240-275`），历史/其他 writer 与迁移必须分别查明。completed feed 解码拒绝 `prompt`、`response`、`credential`、`upstream_error` 等原始字段且不接受未知字段（`internal/completedfeed/contract.go:204-224,335-366`）。`internal/admin/audit_handlers.go:265-315` 将调用者给出的 detail/before/after 直接序列化，内容策略 handler 只传 config/status（`internal/admin/content_policy.go:85-90`），新策略 handler 必须保持此边界。网关有将 Adapter 解析错误 `%v` 写入应用日志的路径（`internal/gateway/relay.go:1433-1451`）；Anthropic adapter 某些错误包含 Provider 提供的 quoted 枚举值（`internal/adapters/anthropic_native.go:163-166,240-247`），需对这些字符串做负向探针与安全摘要，不能仅依赖内容对象的 disabled 状态。

**已验证的额外正文 writer：Exact Response Cache。** `internal/responsecache/service.go:39-46,377-402` 将原始 `SourceResponse` 装入加密 record，`internal/responsecache/redis_backend.go:56-82` 写入 Redis；调用方 `internal/gateway/invocation_optimization.go:343-453,720-752` 在独立默认关闭的 canary/opt-in/persistence_allowed 条件下可读 hit 或提交 miss。它的开关与当前 `contentcapture.PolicyStore` 无交叉检查。故 D12 关闭后续正文时，必须在取得 cache hit/owner **之前**核对有效内容禁存状态，并在异步 commit 前重新确认没有中途禁存；禁存应 bypass，不妨碍正常 Provider 调用。历史加密 cache 条目不由“关闭未来保存”自动删除；是否仍允许命中或按原 TTL 自然失效须在 UI/合同明示，保守候选是不再读取命中。额度/使用收据仍保留结构化事实，不能清除财务记录。这里需要复用响应缓存正式无副作用检查和真实 Redis 负向验证，不能只断言 content 对象行数为零。

## P2b 机器委托：独立代码前审查输入（未实施）

**已核对的边界。** UR 的 `xinsight_connector_installations` 已保存 `installation_id`、`x_deployment_id`、`org_id`、锚定 `project_id`、`source_instance`、`source_binding_sha256` 和连接状态（M60）；`xinsight_connector_control_bindings` 的 control token 是 UR→XI 控制用途（M61/M62）。XI 的 `connector_installations` 以同一 installation/deployment 身份保存其 workspace `project_id` 和 source instance（XI M21）。UR 的 `xinsight.source.read`／`xinsight.feed.read` 凭据与注册仅授权读取；网关拒绝非空 purpose 的 key 调用模型端点。现有 V2 策略管理 handler 要求 UR 人类 JWT，`audit_logs.user_id` 非空；XI 当前源码未找到策略管理消费者。以上均是本地源码事实，不是 XI/Target 的运行证明。设计复用**配对身份**，不复用已有 control token、source-read token 或其 authority；配对的 `event_scope=model.request.completed` 也不暗含策略权限。

**委托身份与范围。** 由 UR 有权管理员在 UR 管理端对精确 `installation_id + x_deployment_id + source_instance + org_id` 明确授权。当前 installation 的锚定项目仅证明配对关系，不把它误当组织策略的目标项目。新增独立机器 `api_keys.purpose=xinsight.policy.manage`，独立 `ur-xpm1-` token 前缀与 `unirouter.xinsight.policy-manage.v1` 哈希域；复用现有 `receiver_sha256_v1` 的 SHA-256 verifier 加服务器 HMAC 存储原语、32 字节随机 bearer 格式和 staged→active→revoked 生命周期，而不是另造密码方案。XI 生成 bearer、仅向 UR 注册非秘密 verifier；UR 不存 bearer。新 purpose + 独立域 + 精确安装映射一同校验，旧 source/feed token 即使有相同算法也不能进入机器管理路由。`api_keys.project_id` 只是配对锚点，不是目标授权；此 key 永不继承 source/body read、Gateway、Provider、财务或连接生命周期权限。凭据真实注册/激活/交付仍需后续精确批准；本页不创建凭据或指定真实 secret。请求核对 `status=feed_active`、installation `desired_state=active` 且未被明确撤销/断连、当前 source instance 与配对摘要一致、组织 active；`observed_state=provisioning/abnormal` 是同步健康而非独立授权，不单凭暂时异常撤销策略修复能力。`observed_state=disconnected` 或配对完整性/身份失效属于信任失败，拒绝；`desired_state=paused/disconnected` 同样拒绝。重新配对、XI deployment/source instance 改变或锚定项目失效均使旧委托停止生效，绝不自动迁移至新 installation。

委托行按 `(installation_id, org_id, target_kind, coverage, exact_project_id?, exact_user_id?)` 定义，`target_kind` 只有 `enterprise_default`、`project_policy`、`user_exception`；动作分别列 `read`、`write`，写不隐含其他作用域写权。`coverage=exact` 限定一个现存项目（user 再限定一个当前成员）；`coverage=all_current_future` 只能由仍有效的 UR `org_admin`／`platform_admin` 在精确组织授予项目或用户类，运行时按**目标项目当前 org_id**匹配，因此未来新项目自动纳入，跨组织和已停用项目不纳入。组织级 `enterprise_default` 只对应企业默认行；将“所有当前及未来项目沿用同一默认”实现为写企业默认，而非批量制造显式项目行。确需 XI 将来修改任何项目的显式覆盖，另授权 `project_policy/all_current_future/write`；用户例外的全部项目/未来用户也必须是**单独**可见的显式授权，不随项目权自动附赠。组织管理员可以同时授予企业写与全项目发现，XI 才能呈现完整“未来项目全选”；项目管理员只可授予自己仍管理的精确项目及该项目用户，不可授予企业或未来项目谓词。每项委托有稳定 ID、递增 revision、`active/revoked`、授权者 UR user ID、时间及可选失效时刻；撤权保留记录，不删审计。

**人类授权与凭据入口。** UR 人类 JWT 管理端新增 `GET /api/v2/organizations/{org_id}/xinsight-policy-delegations?installation_id=...`、`POST /api/v2/organizations/{org_id}/xinsight-policy-delegations`、`PUT /api/v2/organizations/{org_id}/xinsight-policy-delegations/{delegation_id}` 和 `POST /api/v2/organizations/{org_id}/xinsight-policy-delegations/{delegation_id}/revoke`；后两者携 `expected_revision`，撤权不删除，冲突 409。创建体显式列 installation、目标种类、coverage、project/user ID、read/write 动作和可选到期日，响应返回完整 scope、grantor 和 revision，不返回任何 bearer。`GET/POST /api/v2/organizations/{org_id}/xinsight-policy-credentials` 展示绑定/状态并接收 XI 生成的非秘密 registration；`POST /.../credentials/{key_id}/activate` 与 `/revoke` 完成轮换，激活新 key 时旧 key 原子撤销或按现有 A/B 凭据窗口实施有界重叠，不能默许双活无限期持续。所有变更经现有 UR 人类 JWT、提交时再授权和审计；管理端 UI 必须显示配对 installation/deployment/source instance、锚定项目、每项 scope/action、`all_current_future` 对以后项目的含义及 credential 指纹，在操作员确认后调用上述入口并回读 revision。项目管理员 UI/API 不提供未来项目谓词。凭据注册/轮换与 grant 是两个独立动作；凭据 active 本身没有委托。政策全未来项目只扩大**策略发现/读写**范围，不创建 XI source、feed credential、项目连接或正文读取权；这些仍按原合同单独接通。公开 OpenAPI 与 UI 文案在实施时同步更新。

| 主体 | 可以做的事 | 必须拒绝 |

每个机器 PUT 在**同一数据库事务**里重新锁定并核对：精确 key/purpose/status 与配对身份、installation/组织/目标项目、指定 delegation ID/revision/action、授权者当前 active 状态及原 scope 所需的 org role 或 project membership、目标 user 当前组织/项目成员资格，最后才执行现有 P2a `PutEnterpriseTx`／`PutScopedTx` 的 ref/version/vector CAS，并写服务身份审计及幂等回执。授权者失权先提交则 PUT 拒绝；PUT 先提交则之后的撤权阻止下一次提交。GET/分页发现也按当前权限重验并使用 `Cache-Control: no-store`；无权限目标与不存在目标对机器返回同形 404，凭据错误 401，已认证但失效委托 403，版本/绑定变化 409，存储或授权读失败 503。

**锁序和竞态合同。** 认证阶段可无锁读取 key→installation→grantor ID，但该快照只用于定位锁，绝不授权。写事务先按 ID 升序取得 `principallock.LockUsers`（机器为 grantor 与目标 user；人类 grant/凭据变更为 actor、相关 grantor 与目标 user），再按现有 `reauthorizeCommittingActorTx` 的顺序读取/锁定 live users 与人类 exact session，之后才锁 target org/project 与 membership；接着按固定 `installation → api_key → delegation → operation_ref` 顺序锁行，最后进入 P2a scope CAS/审计。锁后任何预读 ID、revision、binding 不一致即回滚 409/403，不在已持锁事务里重新发现另一 grantor 再倒序锁。要让此序列成为真实保证，实施时必须检查并按需改造 credential revoke/rotate、delegation revoke、connector pause/disconnect 这几条写路径，使其在操作同一行前遵循同样的 user-lane→org/project→installation/key/grant 序；否则不能声称撤权竞态已闭合。项目管理员授予精确项目时也调用现有 `reauthorizeCommittingActorTx` 项目要求。新路由不能通过从源 token 或 XI operator 字段导出 UR 人类 context 绕开该序列。

**机器 HTTP 合同（示例 ID 均虚构、无凭据）。** 保留现有 UR 人类 V2 管理路径；新路由只由独立 purpose 中间件进入：`GET /api/v1/integrations/xinsight/payload-policy/scopes?cursor=...` 分页发现组织内当前可见项目及其适用 grant，`GET/PUT /api/v1/integrations/xinsight/payload-policy/organizations/{org_id}` 读取/写入企业默认，`GET/PUT /api/v1/integrations/xinsight/payload-policy/projects/{project_id}` 读取/写入项目行，`GET/PUT /api/v1/integrations/xinsight/payload-policy/projects/{project_id}/users/{user_id}` 读取/写入个人例外，`GET /api/v1/integrations/xinsight/payload-policy/operations/{operation_ref}` 查询本 installation 的提交回执。用户发现用单独 `GET /api/v1/integrations/xinsight/payload-policy/projects/{project_id}/users` 有界分页，仅返回授权可见的当前成员 ID/安全显示名，不返回 key、secret、正文或全组织用户目录。列表的 `all_current_future` grant 是动态谓词，每页重新检查；新的项目无需人工逐项授权。路径 ID 只用于选择目标，真实组织和配对从认证映射取得。operation GET 也重新检查当前 credential、installation、delegation 和目标 scope 的 read 权；撤权后不能凭旧 operation ref 继续读取回执。
