# UniRouter Agent 执行与复核协议

**版本：** 2.3
**生效方式：** User 已确认单一执行负责人流程；与适用的全局及项目 `AGENTS.md` 一起使用，遵循平台实际指令优先级。入口、历史记录和本协议中的风险示例不覆盖项目明确的批准或编码前独立审查要求。

---

## 1. 目标

UniRouter 采用一个执行负责人完成计划、实现、验证、仓库集成和已授权环境操作，避免把一个批次拆成多次人工传话。

同一时间只保留一个 Active Milestone。它是完整授权目标中当前最小、
可独立验收的结果，不等于缩小用户目标；独立后续项不会被静默并入当前 diff。

当前执行负责人是 **Codex**。Canary、Sentinel、Atlas 不再是批次继续推进的强制关卡；它们或其他人员/agent 可以按需承担独立复核。

本协议不取消以下边界：

1. 自动化测试和 GitHub 强制 CI 不能被角色判断替代。
2. 同一执行负责人完成的实现和测试不能标记为“独立复核”。
3. 生产、高影响数据、凭证和付费外部动作仍需要 User 明确授权。
4. `Local verified`、`CI verified`、`Target verified`、`Production verified`、`External integration verified` 必须分别记录，不能互相推导。

---

## 2. 责任模型

| 角色 | 责任 | 边界 |
|------|------|------|
| **User** | 确认 PRD/范围；批准生产和其他高影响外部动作；决定是否接受剩余风险 | 不需要在 agents 之间搬运常规上下文；不得用一句“都完成了”替代证据 |
| **Codex / 执行负责人** | 计划、开发、测试、文档、本地分支，以及当前请求或持续授权明确覆盖的提交、PR、CI、合并、部署、运行时验证和证据 | 不绕过强制 CI；不把自测写成独立验收；不从“继续”推定新的外部写权限 |
| **独立复核者** | 按执行记录复跑测试、代码审查、集成审查、目标环境检查或安全检查 | 项目 AGENTS.md 规定的审查必须按其时点完成；其他复核按需进行；核实并裁定的当前阻塞影响对应动作，不扩大产品范围 |

Canary、Sentinel、Atlas 名称保留为历史角色和可选复核画像：

- Canary 画像：功能、回归、产品语义和边界复核。
- Sentinel 画像：Git diff、PR、分支保护和 CI 复核。
- Atlas 画像：部署、运行时、目标环境、回滚和清理复核。

任何具备能力的复核者都可以执行这些检查，不再要求由特定名字的 agent 完成。

---

## 3. 风险分级

| 等级 | 范围 | 执行要求 |
|------|------|----------|
| **R0 本地整理** | 拼写、链接、索引、无事实状态变化的文档整理 | 聚焦核对和 `git diff --check`；无需单独批次证据 |
| **R1 常规产品变更** | 可逆的 UI、API、路由、Provider/Model Profile、测试和事实源变化，且不命中升级类别或项目 AGENTS.md 的独立审查触发项 | 聚焦回归；候选稳定后完成与影响面相称的必需检查；有授权时按稳定问题批次 push/CI，仅因新变化、失败或未解决风险追加验证 |
| **R2 升级验证** | 明确的 migration、security、identity/authorization、financial，或不可逆变化 | 独立切片；增加真实前态/负向状态、回滚或恢复、独立复核及必要目标证据 |
| **R3 外部状态** | 供应商实测、云端部署、数据或流量改变、Production/External verified 声明 | 先核对精确目标和当前授权；记录版本、环境和实际结果；验证强度仍由变化本身的 R0-R2 风险决定 |

不确定是否命中 R2 时先查代码、迁移和实际写边界；只有证据仍无法排除时才按 R2。无需固定频率的 alignment 仪式。

## 4. 已授权的默认动作

在已确认范围内，执行负责人可以直接执行：

1. 读取和修改 UniRouter 工作区文件。
2. 运行本地测试、构建、静态检查和浏览器验证。
3. 创建本地 `codex/` 分支并保留用户已有工作树修改。
4. 在当前授权范围内维护必要的代码、测试、文档和本地验证结果。

以下动作仍需 User 对具体动作明确授权：

1. 提交、推送、创建或更新 PR、合并、发布以及任何环境部署，除非当前请求或既有持续授权已经明确覆盖。
2. 每次生产部署、生产回滚或生产流量切换。
3. 目标数据库破坏性操作、不可逆迁移、目标恢复或数据删除。
4. 创建、禁用、轮换或暴露凭证、密钥、令牌、DSN。
5. 扩大已批准的数据导出范围，或启用 raw prompt/response 等敏感数据模式。
6. 超出既定模型、请求次数或费用上限的真实供应商调用。
7. 公开发布、开源切换或外部可见权限变更。

无权限、无凭证或无批准是具体动作的外部阻塞，不是整个任务的停止条件。报告准确缺口；需要恢复的批次记入既有执行记录，其余独立、已授权工作继续。

## 5. 标准执行流程

下列步骤按当前任务及授权适用；讨论和审查默认只读，普通修改不自动创建验收矩阵、PR、部署或长期记录。

1. 从当前请求、已有决定和必要事实明确目标、范围与验收；同类长任务先读相关复盘及其生效入口，只在影响下一步时核对远端状态。
2. 命中项目 `AGENTS.md` 审查触发项时，先完成对应的独立只读审查；其余独立工作可继续。
3. 完成必要修改和定向验证，候选稳定后完成适用的必需检查。只有新变化、失败或未解决风险才追加或重复验证。
4. 仅在当前授权覆盖时提交、推送、创建或更新 PR。适用 required CI 通过，且合并获授权后才合并；通过 CI 本身不授予合并权限。
5. 当前目标需要 Target 证据时，核对该环境的精确访问和授权；完成已授权部署与验证。缺口只暂停依赖步骤。
6. 区分证据层级并更新确有变化的事实。长任务按 6.4 复盘并完成本次验收必需的改进；当前请求仍有已授权、未阻塞的必要工作时继续，全部完成后停止，不自动吸收下一批独立需求。

未命中明确前置要求的独立复核可以异步发生，不作为默认串行关卡。已明确要求的编码前审查不能用事后复核替代。

## 6. 记录与证据

### 6.1 当前执行记录

`docs/agent-workflows/EXECUTION-RECORD.md` 是长时间、跨外部生命周期或需要恢复的批次事实源。普通本地修改无需为了形式完整性改写它。使用时至少包括：

1. 批次、范围、风险等级和状态。
2. 基线分支/commit、当前分支和预期 PR。
3. 修改文件和行为变化。
4. 非目标和边界。
5. 实际执行的命令、结果和未执行原因。
6. CI、合并、部署和外部集成状态。
7. 批准、停止条件、回滚和清理要求。
8. 已知缺口和下一步。
9. 可供复核者直接执行的检查清单。

### 6.2 不可变证据

R2 风险、部署、不可逆动作或外部集成达到重要事实节点时，在 `docs/ops/evidence/` 增加带批次和日期的证据文件。普通可逆本地修改以测试输出和精确 diff 为充分证据。已有证据不覆盖、不回写新历史；后续修复通过新文件引用旧证据。

运行时或外部交换证据还应记录适用字段：

- 环境用途和非生产/生产分类；
- commit、镜像或部署版本；
- 时间、命令、健康检查和实际结果；
- request ID、exchange ID、artifact hash 或 receipt ID；
- 数据最小化、脱敏和保留期；
- 回滚/停止条件和清理状态。

### 6.3 状态词汇

| 状态 | 允许的事实含义 |
|------|----------------|
| `Planned` | 只有已确认范围，无实现证据 |
| `Implemented` | 代码已修改，尚未完成要求测试 |
| `Local verified` | 执行负责人完成记录中的本地验证 |
| `CI verified` | 对应提交通过仓库强制 CI |
| `Target verified` | 指定非生产/批准目标环境有实际证据 |
| `Production verified` | 指定生产或明确生产等价环境有实际证据 |
| `External integration verified` | 外部系统导入/回读/receipt 已完成并可核对 |
| `Blocked` | 缺少明确的权限、批准、环境、凭证或外部结果 |

可以同时保留多个层级，例如 `CI verified; target pending`。不得因为 CI 通过就写 `Target verified`，也不得因为某个 agent 声称完成就写 `Production verified`。

### 6.4 长任务完成复盘

长任务完成前，在已有执行记录中简要核对五项：目标、实际结果及各层证据；偏差及失败类别；错误假设和原检查为何未拦截；本次必需的原代码、测试或交付入口改进及其验证（可行时证明旧失败、新通过）；剩余项、负责人和下一动作。同类问题再现时，先核对上次改进实际生效的入口，解释未覆盖原因并修正该入口。当前验收必需的改进完成后才报告完成；独立优化不扩入本批。没有新增教训可明确记录“无需新增”，不为复盘形式另建测试、框架或台账。

## 7. 独立复核流程

审查触发项、时点、独立性、对象绑定、去重和最多一次收尾审查，以项目 `AGENTS.md` 第 4 节为准。按对象需要读取已有执行记录、设计、diff 和实际验证证据；编码前不要求先生成代码提交、CI 或 Target 结果。

复核结果写入 `docs/agent-workflows/reviews/<batch-id>-<reviewer>-<YYYYMMDD>.md`，记录复核者、独立性、精确对象、实际检查、证据边界和结论，不覆盖其他结果。格式见 `reviews/README.md`。

发现处置使用 `validated_blocker`、`validated_required`、`valid_deferred`、`rejected`、`product_decision_required`。P0–P3 仅用于已核实发现的严重程度，不能凭标签生成新产品要求或外部授权。执行负责人核实并裁定：

- 当前已验证的 P0/P1 阻塞在相关合并、部署或验收前处理；发布后问题进入单独纠错批次，保留原证据，不静默重开已完成 PRD。
- 当前验收必需项进入本次实施；独立后续项简要记录，只有确需持续跟踪的有效问题才进入已有 `OPEN-ISSUES.md` 或 backlog。
- 新的产品取舍请求对应决定，只暂停依赖它的工作。其余新非阻塞发现默认延期。

`VERIFY-RESULT.md` 保留协议 v1.x 的历史验收结果，不作为当前串行门禁，也不由多个复核者覆盖。

## 8. GitHub 与合并规则

1. 不直接推送 `main`。
2. 分支默认使用 `codex/<scope>`。
3. 提交前检查工作树，不能回退或覆盖不属于当前批次的改动。
4. PR 必须说明范围、风险、测试、证据、非目标和目标环境状态。
5. UniRouter 当前强制 CI 包括 `Change Routing` 和它判定适用的 `Backend Tests`、`Frontend Build`、`Docker Build`；适用检查通过后才可合并。纯文档 PR 只能由路由显式跳过昂贵任务。
6. 合并后以 `origin/main` 的实际 commit/PR 为准更新状态，不以本地分支 SHA 猜测。
7. 强制推送、删除远端保护分支或绕过检查不在默认授权内。
8. 保留现有 exact-main 协议检查及 required checks 的实际覆盖；不因减少费用而自行降低。未知 Browser 路径保守验证；本次规则修订不减少 Bundle 的 Backend 验证。昂贵 CI 前核对预算与用量，不自行提高预算，不采用 ECS self-hosted runner。

---

## 9. 部署、凭证与数据安全

1. 凭证只通过 SSH agent、钥匙串、环境变量或批准的秘密管理方式注入，不写入聊天、Git、共享 Markdown 或 evidence。
2. 非生产环境必须有明确用途标签；无法确认环境性质时停止部署。
3. 部署前记录当前版本、健康状态和回滚方式，部署后验证关键健康/API/UI 路径。
4. 数据导出遵循明确 request ID、批准 manifest、脱敏和最小化原则；不得把 Gate A 扩大为广义数据发现。
5. UniRouter 和 X-Insight 是独立项目。共享文件夹只承载沟通、合同、最小化数据交换和回执，不替代各自仓库、CI、数据库或发布治理。

---

## 10. 流程迁移

- 协议 v1.x 的 Canary/Sentinel/Atlas 完成记录继续作为历史证据，不重写。
- `FIX-SIGNAL.md` 保留为旧链接兼容入口，新的当前执行事实写入 `EXECUTION-RECORD.md`。
- `VERIFY-RESULT.md` 保留最近一次 v1.x 独立验收结果。
- 新复核统一写入 `docs/agent-workflows/reviews/`。
- 当前事实以 `CURRENT-STATUS.md`、相应 PRD acceptance matrix、`EXECUTION-RECORD.md` 和不可变 evidence 交叉核对。
