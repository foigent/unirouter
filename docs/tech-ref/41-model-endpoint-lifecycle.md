# 模型与端点：产品与运行时合同

本文定义本地单客户部署中，从接入一个供应商模型到形成可用路由的唯一产品合同。页面、API、发布记录和网关都必须使用这套关系，不再各自推导“已启用”或“可调用”。

## 1. 一个公共模型，多个供应商端点

```text
公共模型 ID（应用请求中的 model）
  ├─ 供应商端点 A（官方 API）
  │    ├─ Base URL / 协议适配
  │    ├─ 上游模型或部署 ID
  │    └─ 一个或多个加密凭证
  ├─ 供应商端点 B（OpenRouter / 百炼 / Azure 等）
  │    └─ 自己的地址、上游 ID 和凭证
  └─ 当前发布
       ├─ 稳定路由
       └─ 可选的灰度路由
```

- `public_model` 是稳定的对外 API 身份。大小写、空格和连字符不同但语义等价的名字不能创建为两条活跃模型记录。
- `upstream_model` 是某个供应商实际接受的模型名或部署名，通过 `model_mapping` 映射。
- 同一个 DeepSeek、GPT 或其他公共模型来自多个 MaaS 时，应增加供应商端点，不应复制公共模型。
- 历史发布是不可变审计记录，不是当前模型或当前端点的重复项。

## 2. 日常页面与高级运营

侧栏只保留一个日常入口“模型与端点”。该页面包含三个同页标签，不再要求用户在多个二级页面之间猜流程。

### 模型与路由

这是默认工作区，完成以下全部日常操作：

| 可点击位置 | 作用 | 保留的上下文 |
| --- | --- | --- |
| 新增供应商端点 | 新建公共模型，或为已有公共模型增加供应商 | 公共模型、供应商、上游 ID、端点地址、协议、路由角色 |
| 管理端点 | 打开一个公共模型下的全部供应商端点 | 精确公共模型 |
| 真实检测 | 只检测所点的“端点 × 公共模型” | 精确 channel、public model、mapped upstream model |
| 补齐端点检测证据 | 逐项检测所有缺少当前成功证据的端点 | 每项独立请求与独立结果 |
| 首次启用 | 在尚无稳定发布时创建第一条稳定路由 | 服务端生成发布标识并固定连接版本 |
| 加入 5% 灰度 | 已有可用稳定路由时加入新端点 | 稳定路由保留，候选只接收 5% 流量 |
| 替换失效路由 | 有稳定发布记录但已无网关候选时恢复 | 旧发布原子转为已回滚，新发布原子成为稳定路由 |
| 紧急暂停 / 恢复连接 | 停止或恢复某个供应商连接 | 发布历史不删除；恢复前要求当前成功检测 |
| 管理此端点凭证 | 打开同页“凭证”并锁定精确端点 | `channel_id` 与公共模型 |
| 诊断此模型连接 | 打开同页高级连接诊断 | 精确端点与公共模型，不要求项目或应用 |

### 凭证

凭证仍是独立安全对象，但在“模型与端点”内嵌显示：

- 从端点进入时，只加载和编辑该端点的凭证；不会让另一个活跃端点阻断当前端点的新增凭证。
- Key 只在输入时出现，服务端加密保存且永不回显。
- 活跃路由所使用的连接不能直接改密；需先通过发布或紧急暂停把变更置于安全状态。
- “查看全部凭证”才退出精确端点上下文。

### 高级运营

高级运营只有三个用途：

1. 模型目录与项目范围：显示名称、生命周期、能力声明、项目可见范围；不重复显示发布工作区。
2. 调用条件诊断：区分连接是否就绪与某个项目/应用/API Key 是否可调用。
3. 发布与回滚证据：查看不可变的候选、灰度、稳定、回滚和拒绝记录。

这些功能保留在同一页面内，不新增侧栏页面。日常新增、检测和启用不需要进入高级运营。

## 3. 唯一状态链

```text
端点配置
  → 可用凭证
  → 当前真实检测
  → 发布槽（稳定 / 灰度）
  → 网关实际候选
  → 模型生命周期
  → 项目 / 应用 / API Key 调用准入
```

任何中间对象都不能单独冒充最终状态：

- “凭证可进入候选”只说明 Key 当前可用，不等于端点已发布。
- “真实检测通过”只说明该精确供应商请求成功，不等于已进入路由。
- “有稳定发布记录”不等于网关当前有候选；连接暂停或固定版本漂移时，状态是“路由异常”。
- “路由可用”只说明网关至少有一个候选，不等于任意项目、应用或 API Key 都有调用权限。
- “项目可调用”必须由调用条件诊断结合项目目录、应用授权和 Key 范围判断。

## 4. 页面状态的服务端定义

服务端投影按以下优先级生成模型状态：

| 状态 | 条件 | 主要动作 |
| --- | --- | --- |
| 治理阻断 | 精确公共模型已退役 | 在高级运营中复核生命周期 |
| 灰度中 | 存在有效稳定发布和灰度发布 | 提升或回滚 |
| 稳定路由 | 稳定发布存在且网关至少有一个候选 | 可增加供应商端点或发起灰度 |
| 路由异常 | 稳定发布保留但网关没有候选 | 检测目标端点后“替换失效路由” |
| 兼容路由 | 网关有候选但尚无确定性发布记录 | 在高级发布中收敛历史配置 |
| 可启用 | 凭证与当前真实检测均有效，尚未发布 | 首次启用 / 灰度 / 恢复 |
| 检测失败 | 最近一次精确检测失败 | 修复地址、模型 ID、参数或供应商权限后重测 |
| 待检测 | 有可用凭证但没有当前成功证据 | 真实检测 |
| 缺少凭证 | 没有启用、未冷却且允许该模型的 Key | 管理此端点凭证 |
| 已暂停 | 连接配置为 disabled | 检测后恢复连接 |
| 版本不一致 | 发布固定的连接版本与当前配置不一致 | 刷新后按发布流程重建候选 |
| 尚无端点 | 目录中有模型但没有供应商连接 | 新增供应商端点 |

“路由可用”和“所选主体可调用”必须分别展示，不得再合并成一个模糊的“已启用”。

## 5. 发布终态与失败恢复

- 发布标识由服务端生成，用户不手填。
- 身份冲突、检测证据过期、连接版本冲突或激活失败时，自动生成的候选必须进入 `rejected`，不能停留在 draft / validated 形成“待处理垃圾”。
- 手工创建但决定不再推进的 draft / validated / shadow 可“终止候选”，同样进入 `rejected` 并保留原因与事件。
- `active`、`canary`、`rolled_back` 和 `rejected` 都是有审计意义的状态；历史记录不能删除或复用。
- 失效稳定路由的替换必须在一个数据库事务中完成：旧稳定发布转为 rolled_back、稳定槽切换、新发布转为 active。任一步失败时三者全部保持原状。
- 当灰度存在时，普通回滚不得并发清除稳定槽。

## 6. 身份冲突

在创建端点、修改端点模型、首次启用、开始灰度或恢复失效路由之前，服务端都要执行公共模型身份预检。

例如 `DeepSeek V4 Flash` 与现有 `DeepSeek-V4-Flash` 等价时：

- API 返回结构化 `model_identity_conflict`；
- UI 指向现有 canonical ID；
- 不创建发布草稿；
- 用户应在该公共模型下增加新的供应商端点。

精确同名但已退役时返回 `model_retired`，不能通过换大小写或分隔符绕过生命周期。

### 6.1 稳定请求身份与不可变 successor

当已有稳定请求名必须绑定新的不可变公共模型身份时，用户请求身份与
canonical 审计身份必须分离：

```text
稳定请求名 glm-5.2
  → primary Alias
  → canonical successor glm-5.2-20260902
  → 精确 Deployment / Profile / Release
```

- successor 在切换前保持 `staging + approved_catalog=false`；可以完成
  Deployment、Probe、approval 和 sealed initial Release，但不能预先获得
  stable Slot，也不能仅靠目录隐藏阻止直接执行。
- 已经发布过的 predecessor 与从未激活的 staging predecessor 使用不同的
  receipt version、operation scope 和 idempotency namespace。后者只有在
  `Slot=0`、sealed/可执行 Release=0、active Alias=0、completed successor
  receipt=0 时才允许切换；失败 Probe 与 Deployment 历史可以保留，但不能
  被误解释为执行权威。
- 首次切换由一个服务端领域命令完成：锁定并核对旧、新模型、Alias、
  Release/Slot 和受影响 model-set 的完整 before-state，在同一 PostgreSQL
  事务中激活 successor stable Slot、退役并下架 predecessor、创建一个
  immutable primary Alias、把直接 model-set 引用改为稳定 Alias，并写入
  完整不可变收据。任一步失败时不得留下半切换状态。
- 普通 Gateway 调用若绕过稳定请求名直接指定受 primary Alias 保护的
  canonical successor，必须 fail closed。`/v1/models`、项目 Catalog、
  Developer Console 和 API Docs 在完成调用者授权后投影 `request_model`；
  只有管理员投影可以同时显示 canonical identity 和历史关系。
- primary Alias 不能通过通用 Alias CRUD 改写或停用。已经完成切换的
  predecessor 不能复活，successor 不能回到 staging 或被直接删除；后续
  Alias retarget 是新的版本化生命周期问题，不属于任何 first-cutover
  合同。published predecessor v1 与 never-activated staging predecessor v2
  不能交叉重放或共用 parent/child receipt。
- 请求重放返回相同收据；commit 结果不明确时只通过 parent lifecycle
  receipt 与完整 child evidence 回读恢复。提交后的读回故障不自动回滚
  已生效身份，必须依据不可变收据确认新状态后 forward-fix。

## 7. 真实检测合同

- 单项检测只发送一个公共模型；模型映射后把精确 `upstream_model` 发给供应商。
- 返回和审计同时记录 public model 与 upstream model。
- 批量检测是多次单项检测，不是一条请求，也不能用列表第一项的结果代替其他模型。
- 检测证据绑定 channel、public model、upstream model、routing epoch、credential fingerprint 和测试参数版本；任一项变化都会使旧证据失效。
- 未知供应商错误在日常页只显示用户可操作摘要；原始原因代码留在高级诊断。

## 8. 不变量

1. 一个客户部署中的同一语义模型只有一个活跃公共模型 ID。
2. 一个公共模型可以有任意多个供应商端点；每个端点独立配置、凭证、检测和路由角色。
3. 新端点固定从 staged 开始，不能因保存成功直接承载流量。
4. 每次检测、启用、暂停、灰度、提升、回滚和拒绝都针对明确的模型与端点，并留下审计证据。
5. 页面状态只来自服务端聚合投影；前端不得把通道、Key 或发布列表自行拼成另一套“真相”。
6. 网关路由、模型治理和调用准入是三层不同事实；UI 必须明确其关系而不是重复显示互相矛盾的“已启用”。
