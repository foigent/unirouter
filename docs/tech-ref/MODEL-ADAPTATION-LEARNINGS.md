### MAR-001 Validate capability composition under effective defaults

- Invariant: A Profile may expose only request combinations that its exact provider surface can execute; individually valid capabilities do not prove their composition under omitted fields or provider defaults.
- Scope/Trigger: Any model Profile that combines reasoning defaults or toggles with tools, tool choice, structured output, streaming, media, cache or search.
- Enforcement: Typed normalization rejects impossible combinations before Freeze or credential use, and full prepare/admission/provider-payload regressions cover both omitted defaults and explicit overrides. A canonical connectivity Probe that would inherit an incompatible provider default may add only an exact Profile-owned override validated against the typed reasoning contract; its persisted safe request summary records the effective control without retaining prompt content or credentials.

### MAR-003 Share provider wire normalization between probe and runtime

- Invariant: A safe provider wire variation with unchanged canonical semantics is normalized at the lowest shared exact-scoped boundary available; cross-role framing, usage and terminal lifecycle facts use one exact-binding-selected mechanical state. Probes add semantic assertions and never become proof of software-artifact correctness. Where role-specific full-envelope validators remain, cross-delivery fixtures and public execution evidence are mandatory and a third provider-specific full envelope parser is a stop condition.
- Scope/Trigger: Typed provider probes and runtime delivery encounter the same provider-specific response variation, especially function tools, structured output, streaming and media.
- Enforcement: Exact-scoped normalizers validate duplicate JSON members before any map decoding, remove only safe provider wire variations and retain unknown siblings for the canonical guardrail. DeepSeek V4 and the exact Kimi K2.6/K2.7 Code/K3 non-stream function-tool contracts accept only a lexical non-negative child tool-call index and remove it before canonical delivery validation. Kimi non-stream runtime and Probe share one exact-binding-selected document-ambiguity/index-preparation result. Current Kimi K2.6/K2.7 Code/K3 streaming Runtime and Probe share bounded SSE event assembly, exact-binding preparation, provider/cache usage comparison and terminal-DONE state; K2.6 removes only an empty-string delta reasoning member, while K2.7/K3 retain reasoning for typed Probe and canonical delivery checks. The current exact DeepSeek V4 Flash/Pro Chat v4 operation paths project Runtime and Probe role-owned validated frame facts into one binding-selected lifecycle engine: Runtime preserves its existing first-DONE and latest-choice clean-EOF compatibility policy plus provider cache hit/miss authority, while the immutable generic Flash attachment remains on the existing generic Runtime path and immutable Probe v1/v2 preserve separate usage shapes, model/content assertions and whole-body diagnostics. The production DeepSeek Probe consumes the complete compiled binding instead of selecting mechanics from contract/model alone. MiniMax M3 and GLM 5.3 Function Tools qualification share one exact-binding-selected request builder and adapter-normalized validator while retaining separate Probe identities for output-limit, reasoning, tool-choice and response-replay differences. MiniMax PAYG M3 reuses those mechanics under a new immutable access-surface Probe identity; PAYG M2.7 and M2.7 Highspeed share one parameterized M2 mechanics contract whose exact Profile/upstream tuples and reported models remain independently fail-closed. GLM 5.2/5.1/5-Turbo/5 and 5V-Turbo reuse the same validator mechanics under a toggle-family Probe identity while retaining exact Profile/upstream tuples, reasoning and media contracts; immutable protocol successors explicitly model Function Tools without reinterpreting the earlier GLM 5.3/M103 protocol identities. The cross-delivery fixture proves the same normalized responses traverse canonical Runtime inspection without granting an unmodeled media-plus-tools or generic GLM response contract. Runtime takes charge authority only from its existing provider usage parser, applies client cache projection afterward and retains guardrail, billing and delivery authority. Ordinary and Unicode escaped-equivalent duplicate-key regressions prevent last-wins normalization. The remaining complete-envelope validation split still requires cross-delivery fixtures and public execution evidence; unknown numeric usage extensions remain non-authoritative. Immutable Probe Contract versions prevent failed historical evidence from being reinterpreted, and a successful capability Probe cannot replace a failed public SDK delivery checkpoint.

### MAR-004 Treat a terminal SSE error as an error after HTTP success

- Invariant: An HTTP 200 that later carries a terminal SSE error must not be projected as an empty successful stream; request identity and safe billing finality remain visible without exposing private content.
- Scope/Trigger: Streaming clients and UI workbenches that consume gateway SSE and may receive an error after response headers or partial output.
- Enforcement: The stream consumer records the terminal error event separately from content and renders its bounded code/message, request ID and billing status; a real `ReadableStream` regression forbids the `(empty stream)` success projection.

### MAR-005 Keep operation protocol identity independent from capability evidence

- Invariant: Capability, catalog and live-evidence state cannot create a deployment operation protocol identity; a typed override must come from one explicit immutable identity declaration, while an invalid or ambiguous declaration fails closed instead of falling back to a generic protocol. Admin capability eligibility must likewise be projected by the service rather than recreated as a frontend Profile/protocol allowlist.
- Scope/Trigger: Canonical onboarding or attachment of a reviewed Profile to Chat, Responses, Messages or another typed operation surface.
- Enforcement: The server first resolves and validates the canonical base operation, then applies only a model-profile-owned exact override. `found=false` returns no fallback identity and preserves the caller-owned Chat, Responses or Embeddings base; resolver errors terminate onboarding. Unverified or legacy Profiles cannot carry typed declarations, and Chat contract registration alone grants no binding authority. The canonical operation projection returns exact `capability_probe_contracts`; the UI renders that projection and has positive Pro/Flash plus unbound-generic regressions instead of owning provider tuples.

### MAR-006 Keep customer sponsorship separate from platform operation

- Invariant: A platform operator may administer a workload-access flow but cannot substitute its own identity for the customer project member who supplies business sponsorship; credential scope can only narrow an approved Grant.
- Scope/Trigger: Platform-admin model validation that creates a workload Application, access request or application credential in another customer organization.
- Enforcement: The UI freezes the exact Application scope, loads only active members from its project, requires an explicit Sponsor, ignores late cross-scope responses and sends a server-normalized model allowlist. Offboarding preserves the backend's structured active-sponsorship diagnosis and directs the operator to revoke the old authorization after any independently sponsored replacement; it never implies that a new Grant detaches the old Sponsor. The backend remains authoritative for Sponsor membership, Grant containment, credential scope and atomic offboarding.

### MAR-010 Publish static capability contracts without rewriting dynamic evidence

- Invariant: A declaration-owned capability contract publication is an explicit, exact-artifact state transition; it must bind the approved Plan to the compiled declaration, complete migration bytes and expected ledger predecessor, while leaving Probe/Approval-owned lifecycle state outside the publisher's mutation authority.
- Scope/Trigger: Publishing or rolling back static capability bindings, current selectors or declared deployment projections after the M100 compatibility baseline.
- Enforcement: Ordinary startup and migration paths reject pending declaration-owned migrations and require a bijection between compiled declarations and exact generated artifact migrations. Publication up/down rejects incomplete validation, projection or verification hooks. The publication owner validates an exact ledger prefix, locks and recomputes the Plan, rehashes the bytes immediately before execution, binds projection predecessors to exact declared effects, verifies final static state in-transaction and performs a same-session readback. Guarded down refuses retained Freeze/provider-attempt execution evidence, and projection planning mutates only absent or `enabled/declared` rows. Current selectors control new attachment eligibility; an exact immutable historical binding remains addressable after its Profile is retired from current, without allowing a new attachment. Generated artifacts are byte-stable with a single terminal newline. Migration regressions select their pre-state explicitly: an exact `RunThrough` ceiling for the historical contract under test, `InstallExactTestArtifact` when current binary behavior requires the complete artifact, and a historical setup ceiling instead of descending through unrelated later business guards. Real PostgreSQL regressions cover non-prefix ledgers, declaration/migration inventory drift, incomplete writer hooks, artifact-byte drift, forged projection predecessors, lifecycle-owned projections, retained execution evidence and actual M101, M102, multi-provider M103, MiniMax PAYG M104, GLM toggle-family M105, MiniMax official-China PAYG endpoint M106 and MiniMax cache-threshold M108 apply/down/reapply cycles.
